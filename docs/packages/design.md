# Publishing the runtimes as packages: design

Status: **designed 2026-10-20; nothing built.** The plan that builds it is
[implementation.md](implementation.md); every outcome here links to the
deliverables that produce it and the scenarios that prove it. Decisions taken
with the user on 2026-10-20: publish to the **public registries**; upstream the
consumer patches **into all five runtimes**; design and plan before code.

Audience: anyone who maintains a runtime here, anyone who uses one from
another repository (the first such **consumer** is

## Vocabulary

| Word | Meaning, and why it matters here |
| --- | --- |
| **Suite** | A YAML file of BDD cases whose steps name **actions**. |
| **Runtime** | One language's implementation of the suite format: parse, lint, run, reports, the test-framework providers and the built-in actions `core.*` and `wait`. Five exist, in `runtimes/{csharp,go,rust,typescript,powershell}`. A runtime knows no product. |
| **Extension** (of a runtime) | A consumer's code that adds actions, context keys and options to a runtime through its public API (`IExtension` in C#). Not the VS Code extension, which this document always calls the **VS Code extension**. |
| **Consumer** | A repository that uses a runtime to run its own suites with its own extension: update2 today, any team tomorrow. |
| **Binding program** | A consumer's own `suiterun`: the runtime's command line with the consumer's extension compiled or loaded in (`Runner.Run(args, ..., new UrpLabExtension())`). The VS Code extension calls it to lint, list and run. |
| **Core spec** | The files every consumer's schema is built from: `spec/core.catalog.yaml` (the core actions), the base suite schema `suite.core.json`, the catalog and diagnostic schemas, and the generator `Build-Schema.ps1`. |
| **Package** | One versioned, immutable archive a language's package manager installs: a NuGet `.nupkg`, an npm tarball, a Rust `.crate`, a PowerShell module `.nupkg`, a Go module version (a git tag the Go proxy serves). |
| **Registry** | The public service a package manager installs from: nuget.org, npmjs.com, crates.io, the PowerShell Gallery, and for Go the module proxy proxy.golang.org reading tags from GitHub. A version published there **cannot be replaced**; it can only be hidden or marked bad (see [5](#5-failure-rollback-and-cleanup)). |
| **Local feed** | A folder on disk that a package manager installs from exactly as from a registry. It lets every package be proved by a consumer **before** anything is published. |
| **Lockstep version** | One version number for the VS Code extension and every package of one release, so "0.7.0" means the same code everywhere. |
| **Trusted publishing** | A registry accepting an upload from a named GitHub Actions workflow by its short-lived OIDC token instead of a long-lived API key. Fewer secrets to leak or rotate. |
| **Patch (P2–P5, R1, R2)** | The numbered local changes update2 carries on its copy of the C# runtime, listed in `update2/test/e2e/UPSTREAM.md`. |

## 1. What we want to achieve

### 1.1 The problem

Using a runtime from another repository today means **copying it**:

* **update2 carries a copy of `runtimes/csharp`** (taken at `e1c4c89`) with
  six local changes. R1 strips inline package versions so its central package
  management restores it (NU1008 otherwise); R2 replaces the build props; P2
  to P5 add features its lab runs need and this repository does not have
  (`--name` case globs, `--progress` live lines through a run observer, and an
  action worker that survives any exception). Every refresh means copying
  three folders and re-applying the patches by hand, and the conformance
  corpus here never sees the patched code. update2 recorded these as requests
  6.1–6.3 and 6.6, "in every runtime".
* **The C# test provider is wired by file path.** A test project references
  `Bdd.Suite.Testing.csproj` and imports its `.targets` by relative path; the
  targets build the generator from `Bdd.Suite.Cli.csproj`. Nothing of that
  works from a package.
* **The core spec needs a checkout.** A consumer's catalog imports
  `spec/core.catalog.yaml` by path and its schema is regenerated by
  `spec/Build-Schema.ps1`. update2 keeps a junction `test/e2e/bdd` to a local
  clone of this repository just to run the generator, and a hand-edited copy of
  the core catalog.
* **No runtime is publishable.** The npm package is `"private": true`, the
  crate is `publish = false`, the C# projects carry no package metadata, and
  the PowerShell module is not laid out for the Gallery. Only Go works by
  version, because the release job already tags `runtimes/go/v<version>`
  (proxy.golang.org lists v0.6.1, v0.6.2 and v0.6.10).
* **The VS Code extension assumes a TypeScript binding in the workspace.** Its
  default linter loads `test/e2e/bindings/typescript/dist/index.js`; a C#-only
  consumer must switch the linter to its own program (update2 does).

### 1.2 Outcomes

| ID | Outcome (observable) | Priority |
| --- | --- | --- |
| <a id="o1"></a>O1 | **A consumer in each of the five languages depends on one released package version** (NuGet, npm, crate, PowerShell module, Go module), builds its binding program and its extension from it, and needs no checkout, copy or path into this repository. | P0 for C#, P1 others |
| <a id="o2"></a>O2 | **C# test generation works from the package alone**: a test project with `PackageReference`s to `Bdd.Suite.Testing` and MSTest (or NUnit, xUnit) gets one test class per suite on every build, under central package management too. | P0 |
| <a id="o3"></a>O3 | **What update2 patches is upstream in all five runtimes**, specified and proved by the corpus: `--name` globs, `--progress` lines through a run observer, the action worker catching every exception. update2 can delete its copy and its patch tests. | P0 (C#), P1 others |
| <a id="o4"></a>O4 | **The core spec comes with what the consumer already installs**: a catalog imports the core without a path, and the schema is regenerated without a checkout. | P1 |
| <a id="o5"></a>O5 | **One release publishes every package at one version, from CI, only after every gate passes**, each package proved from a local feed first; a failure part-way leaves a state that a re-run completes. | P1 |
| <a id="o6"></a>O6 | **Installing the VS Code extension and referencing the packages is enough**: a workspace with no TypeScript binding lints suites in the editor out of the box. | P1 |

### 1.3 Scope and non-goals

In scope: the five runtimes' packages, the four upstreamed features, the core
spec's delivery, the release pipeline, the VS Code extension's defaults for a
package consumer, and update2's move from copy to package (in its own
repository, by its own review).

Not in scope:

* **Changing what suites mean.** No finding code, trace field, report format or
  expression rule changes. The new flags select and observe a run; they do not
  change a case's result or the trace (DEC-P05).
* **A private feed.** Corporate builds that may only restore from an internal
  feed (Azure Artifacts with nuget.org/npmjs upstreams) add the public
  packages as upstream sources; that is the consumer's configuration.
* **Author code signing.** nuget.org countersigns every package (repository
  signature) and npm adds provenance from trusted publishing; an author
  certificate is not planned.
* **Back-porting.** Packages start at the first release after this work; no
  package is built for 0.6.x.
* **Visual Studio and Rider**, as everywhere in this repository.

## 4. Decisions

### <a id="dec-p01"></a>DEC-P01. One package per language, two for C#; the generator ships inside the testing package

* **Choice.** C# publishes `Bdd.Suite` and `Bdd.Suite.Testing`; the other
  languages publish one package each, as in [3](#3-the-shape-of-the-result).
  `Bdd.Suite.Cli` is not a package: its `suiterun` (the core alone) is
  packed **inside** `Bdd.Suite.Testing` under `tools/`, where the targets run
  it as the generator, and every consumer builds its own `suiterun` with its
  extension from `Bdd.Suite`.
* **Why.** A consumer needs the library (for its program) and, in C#, a test
  host that runs at build time; a core-only command line is useful to nobody
  outside this repository, and a separate tool package would be one more
  version to keep in step. In the other languages the generator is the
  runtime's own `suiterun generate`, already in the one package.
* **Trade-off.** `Bdd.Suite.Testing` grows by the generator (framework-dependent,
  about the size of `Bdd.Suite` itself). A later dotnet-tool package can be
  added without changing these two.
* **Supports** [O1](#o1), [O2](#o2). **Verified by** [E1](#e1), [E2](#e2).

### <a id="dec-p02"></a>DEC-P02. Public registries; trusted publishing where offered; names claimed by the first release

* **Choice.** nuget.org, npmjs.com (org `bdd-suite`), crates.io, the
  PowerShell Gallery, and proxy.golang.org through the existing tag. The
  release workflow publishes with trusted publishing (OIDC) on nuget.org,
  npmjs.com and crates.io, and with an API key secret on the Gallery, which
  has no OIDC. Secrets and registry accounts belong to the user; the workflow
  runs in a GitHub **environment** `release` whose protection rule requires
  the user's approval before any publish step.
* **Why.** The user chose public registries (2026-10-20). Any consumer can
  install them, and a corporate feed can mirror them as an upstream. Trusted
  publishing leaves no long-lived key in the repository; the environment gate
  keeps the irreversible step a human decision.
* **Trade-off.** A public version can never be replaced (section 5), so every
  package is proved from a local feed first ([DEC-P09](#dec-p09)). The first
  publish of each name needs a one-time manual setup per registry (create the
  npm org, register the trusted publisher, reserve the NuGet prefix
  `Bdd.Suite` if wanted, create the Gallery key; crates.io accepts a trusted
  publisher only for a crate that exists, so its very first publish uses a
  short-lived token); the plan lists it as an operator step, not code.
* **Supports** [O1](#o1), [O5](#o5). **Verified by** [E11](#e11).

### <a id="dec-p03"></a>DEC-P03. Lockstep versions: every package carries the extension's version

* **Choice.** `package.json`'s `version` is the one source. A script writes it
  into the csproj `Version`, `Cargo.toml`, the runtime `package.json`, and
  `BddSuite.psd1`'s `ModuleVersion`; the Go tag carries it already. CI fails
  when any manifest differs. The TypeScript `apiVersion` (the in-process lint
  contract) stays separate, because it versions an interface, not a release.
  Before 1.0 a minor bump may break the API; the CHANGELOG says what changed.
* **Why.** Five runtimes are proved together by one corpus at one commit;
  one number makes "the C# and Go runtimes of 0.7.0" mean code that agrees,
  and a consumer of two languages pins one number.
* **Trade-off.** A release with no change to, say, Rust still publishes a new
  crate version. Cheap, and it keeps the rule simple.
* **Supports** [O5](#o5). **Verified by** [E10](#e10).

### <a id="dec-p04"></a>DEC-P04. C# packages work under central package management and need no import

* **Choice.** The packages declare dependency **ranges** in their nuspec
  (YamlDotNet `[16.2.1, 17)`, JsonSchema.Net `[7.4.0, 8)`), and
  `Bdd.Suite.Testing` ships `build/Bdd.Suite.Testing.targets` and
  `buildTransitive/` so NuGet imports them automatically. The targets find the
  generator in the package's `tools/` folder by default; this repository's own
  samples set `BddSuiteCliProject` to keep building it from source.
* **Why.** R1 exists only because a **copied project** carries inline
  versions; a package reference resolves under the consumer's
  `Directory.Packages.props` like any other (no NU1008). R2 exists only
  because copied projects inherit the wrong props; a package has no props of
  the consumer's to fight. Both patches disappear by construction.
* **Trade-off.** Two ways to find the generator (package, source) in one
  targets file; the source path is used only by this repository and is
  covered by its samples, the package path by [E2](#e2).
* **Supports** [O1](#o1), [O2](#o2), [O3](#o3). **Verified by** [E2](#e2).

### <a id="dec-p05"></a>DEC-P05. `--name`, `--progress` and the run observer are core flags of every runtime; they select and observe, never change

* **Choice.** Every runtime's `run` and `list` take `--name glob[,glob]`: a
  case is selected when its name matches any glob (`*` and `?`, the glob
  `--path` already takes) **and** the tag filter; a session's selection
  applies it the same way. PowerShell's existing `--test-name <case>` stays,
  as one exact name. `run --progress` writes live lines to standard output
  in one specified shape ([spec/progress.md](../../spec/progress.md)):

  ```text
  StartGroup: <suite>::<case>
      <phase>       <step label> (<action>) <status>[ [<reason>]]
      failure: <message on one line>
  EndGroup: <suite>::<case> [Passed|Failed|Skipped] (<seconds>s)
  Summary: Total=<n>, Passed=<n>, Failed=<n>, Blocked=0, Not Run=0, Skipped=<n>
  ```

  Each library exposes a **run observer** (case started, case finished, each
  trace entry as it is recorded) that the printer is one implementation of.
  The spec says: an observer sees the run and cannot change a result, the
  trace or the report; only cases the filters selected are reported.
* **Why.** update2 needs them (requests 6.1, 6.2) and asked for them in
  every runtime; the format's rule is that one command line means the same in
  all five. The shape is TAEF's console shape, which update2's lab tooling
  already parses, and it is plain enough for any reader. Standard output,
  as update2's patch writes it, because that is the stream its tooling reads;
  reports go to files and `run` has no `--json`, so nothing else is mixed in.
* **Trade-off.** A fixed text shape is now part of the spec; changing it later
  is a spec change. `--name` on `list` lets the VS Code extension run one case
  in every binding, not only PowerShell (`selectsOneCase`), which it may adopt
  later.
* **Supports** [O3](#o3). **Verified by** [E7](#e7).

### <a id="dec-p06"></a>DEC-P06. The action worker turns every exception into a failed step

* **Choice.** Where a runtime runs an action on a worker (thread, goroutine,
  runspace) under a time limit, anything the action throws or panics with is
  caught there and reported as that step's failure with its message; it never
  ends the process. Go recovers panics; Rust catches unwinding panics
  (`catch_unwind`); TypeScript catches any thrown value, including non-`Error`
  values; PowerShell catches terminating errors of any type.
* **Why.** One unexpected exception type ended a whole lab run in update2,
  losing every result and every cleanup still to run (request 6.3). A failed
  step is the format's way to say an action failed.
* **Trade-off.** A truly fatal condition (out of memory, stack overflow) still
  ends the process; no runtime can catch those reliably, and the spec says so.
* **Supports** [O3](#o3). **Verified by** [E7](#e7).

### <a id="dec-p07"></a>DEC-P07. The core spec travels inside every package and the VS Code extension; `bdd-suite:core` imports it

* **Choice.** Every runtime embeds the core spec of its own version (C#
  embedded resource, Go `embed`, Rust `include_str!`, files in the npm
  package and the PowerShell module). A catalog may write
  `imports: [ "bdd-suite:core" ]`; each runtime's catalog loader resolves that
  name to its embedded copy, as the schema generator does. The VS Code
  extension bundles the same spec, including `Build-Schema.ps1`, and its
  default schema generator runs the bundled one. A path import keeps working
  unchanged.
* **Why.** The core belongs to the runtime that implements it: the copy a
  consumer imports must match the `core.*` and `wait` the runtime registers.
  Embedding makes that true by construction and removes update2's junction and
  hand-kept copy. Narrowing the core's `bindings:` lists, which update2 did by
  hand, follows from the importing catalog's own `bindings:` (an imported
  action's bindings are cut to the importer's list).
* **Trade-off.** A small format addition (one reserved import name, and the
  narrowing rule, which applies through `bdd-suite:core` only: a path import
  is the workspace's own file and is read as written), in five loaders, the generator and the VS Code extension's
  index, all covered by new corpus entries. The extension's bundled generator
  must match the runtime version the consumer uses; with lockstep versions
  ([DEC-P03](#dec-p03)) the extension warns when a consumer's package version
  differs from its own.
* **Supports** [O4](#o4), [O6](#o6). **Verified by** [E8](#e8), [E9](#e9).

### <a id="dec-p08"></a>DEC-P08. The VS Code extension bundles the TypeScript runtime as its default linter

* **Choice.** When `bddSuite.bindings.typescript.library` does not exist in the
  workspace, the in-editor linter uses the `@bdd-suite/runtime` the extension
  ships, of its own version. Binding checks (E201, "not implemented by the
  target binding") still need the consumer's binding program, as today.
* **Why.** Linting the format is the same in every runtime (the corpus proves
  it), so the extension needs no consumer code to underline a typo; a C#-only
  consumer gets live lint with zero settings.
* **Trade-off.** The `.vsix` grows by the runtime's `dist/` (a few hundred KB)
  plus `ajv` and `yaml`, which it partly bundles already.
* **Supports** [O6](#o6). **Verified by** [E9](#e9).

### <a id="dec-p09"></a>DEC-P09. Every package is proved from a local feed by a consumer project before anything is published

* **Choice.** `samples/consumers/<language>` holds one small consumer per
  language that references **only** packages (no path into `runtimes/`): its
  own extension with one action, its binding program, and its tests through one
  provider (MSTest for C#). CI packs every package once, puts them in local
  feeds (a folder NuGet source, `npm pack` tarballs, a directory cargo
  registry, a file PSResource repository, a file `GOPROXY`), builds and runs
  every consumer from them, and only then may publish **those same files**.
* **Why.** A registry version is permanent. Packaging defects (a missing file,
  a targets path that only works in this tree, a dependency only a path
  reference provided) are invisible to the runtimes' own tests, which build
  from source.
* **Trade-off.** Five more small projects and a feed per language in CI.
* **Supports** [O1](#o1), [O2](#o2), [O5](#o5). **Verified by** [E2](#e2)–[E6](#e6), [E10](#e10).

### <a id="dec-p10"></a>DEC-P10. Publishing order and idempotence

* **Choice.** After every gate passes on a push to main with a new version,
  and after the `release` environment's approval: publish to crates.io, npm,
  nuget.org and the Gallery, each step first asking its registry whether the
  version exists and skipping it if so; then create the GitHub release with the
  `.vsix`; then the Go tag. The GitHub release and the Go tag are last because
  they announce the release; a consumer never sees a release whose packages
  are missing.
* **Why.** A failure part-way (a registry down, a key expired) must be
  finished by re-running the same workflow, never by bumping the version.
* **Trade-off.** Registries that index slowly (nuget.org can take tens of
  minutes before a version is installable) mean the release notes can appear
  before every package is installable; [E11](#e11) waits for each with a
  timeout.
* **Supports** [O5](#o5). **Verified by** [E10](#e10), [E11](#e11).

### <a id="dec-p11"></a>DEC-P11. What a package contains

* **Choice.** Library code, the command line where the language ships one,
  the core spec, the language README (shown on the registry page), the
  license, and the repository URL. No tests, no corpus, no samples, no
  `artifacts/` or `target/`. C# adds SourceLink, deterministic builds and a
  symbols package (`.snupkg`); npm adds provenance; crates set `include` and
  docs.rs features. Each package's content list is checked in CI against an
  expected list.
* **Why.** A package is what a stranger installs; extra files cost them time
  and leak nothing useful, and a missing file is a defect a list check finds
  before the registry does.
* **Supports** [O1](#o1). **Verified by** [E1](#e1).

## 5. Failure, rollback and cleanup

**A publish fails part-way.** Re-run the release workflow for the same
commit. Each publish step skips a version its registry already has
([DEC-P10](#dec-p10)), so the run completes the rest. The GitHub release and
the Go tag are created only after all four registries succeed.

**A published package is broken.** A version cannot be replaced or reused. The
fix ships as the next patch version; the broken one is hidden from new
installs, by registry: nuget.org **unlist** (and mark deprecated), npm
`deprecate` (unpublish only within 72 hours and only when nothing depends on
it), crates.io `yank`, Gallery **unlist**, Go `retract` in the next `go.mod`.
Existing consumers keep working on the version they pinned until they move.
Who may do this: the registry account owners (the user); the plan names the
command for each.

**Ownership and access.** Package **names** are owned by the registry accounts
that publish them first, not by this repository; the first release claims
them ([DEC-P02](#dec-p02)). Being able to push to `main` does not let anyone
publish: the `release` environment's approval and the registry's trusted
publisher configuration (or the Gallery key) do. A leaked Gallery key is
revoked and replaced on the Gallery; a trusted-publisher rule is removed on the
registry. Nothing here takes ownership of anything a consumer has.

**Consumer rollback.** A consumer that hits a problem moves its pin back
(`Directory.Packages.props`, `go.mod`, `Cargo.toml`, `package.json`,
`RequiredVersion`). update2 keeps its copy until its own E-scenarios pass on
the package ([E12](#e12)); its migration is a change in its repository that
it can revert.

**Local feeds and dry runs** write only under CI's temp directory or the
developer's scratch folder and are deleted with it; no local scenario touches a
registry. A local `npm pack` or `dotnet pack` leaves files under
`artifacts/packages`, which `.gitignore` covers.

## 6. Verification

Local scenarios run on a developer machine and in CI. **Remote** scenarios
touch real registries or another repository and need the user's go-ahead:
[E11](#e11) publishes (irreversible) and [E12](#e12) changes update2. Unit
tests and local scenarios never count as remote evidence.

### <a id="e1"></a>E1. Every package packs with exactly its expected contents and metadata

* **Given** a clean checkout at a commit; .NET 10 SDK, Go 1.24, Rust stable,
  Node.js 24, PowerShell 7.4 with PSResourceGet.
* **When** `scripts/pack-all.ps1 -Out artifacts/packages` packs every package
  (`dotnet pack`, `npm pack`, `cargo package`, `Compress-PSResource` /
  `Publish-PSResource` to a file repository, and a Go module zip).
* **Then** each archive's file list equals its expected list
  (`packaging/<package>.files.txt`), every manifest's version equals
  `package.json`'s, license, README and repository URL are set, no test or
  corpus file is inside, and the core spec is inside each.
* **Cleanup.** Delete `artifacts/packages`.

### <a id="e2"></a>E2. C#: a consumer builds, generates and runs from the packages alone

* **Given** E1's packages in a local NuGet folder feed;
  `samples/consumers/csharp` with a `nuget.config` naming only that feed and
  nuget.org, a `Directory.Packages.props` (central package management), an
  extension project referencing `Bdd.Suite`, a binding program, and an MSTest
  4 project referencing `Bdd.Suite.Testing` with a `bddsuite.tests.yaml`. No
  path leads into `runtimes/`.
* **When** `dotnet build`, then `dotnet test`, then `dotnet test --filter
  TestCategory=smoke`, then the binding program's `lint` and `run --name`.
* **Then** restore succeeds under central package management (no NU1008); one
  test class per suite is generated on build; MSTest reports the expected
  outcomes per case; the guarded suite is inconclusive without
  `BDD_SUITE_ALLOW_GUARDED=1`; the program's lint and run match the corpus
  expectations for the consumer's suites. The same with NUnit 4 and xUnit v3.
* **Cleanup.** Delete the consumer's `artifacts/` and the feed.

### <a id="e3"></a>E3. Go: a consumer builds and tests from the module version alone

* **Given** a file `GOPROXY` holding the module zip E1 produced at the
  release version; `samples/consumers/go` requiring that version, with
  `GOFLAGS=-mod=mod` and `GONOSUMDB` for the module.
* **When** `go generate ./...`, `go build ./cmd/suiterun`, `go test ./...`.
* **Then** generation writes the expected `*_bdd_test.go`; the tests report
  the expected results; no `replace` directive exists.
* **Cleanup.** `go clean -modcache` for the test's `GOMODCACHE`.

### <a id="e4"></a>E4. Rust: a consumer builds and tests from the packaged crate

* **Given** the `.crate` E1 produced, unpacked in the local feed;
  `samples/consumers/rust` depending on `suiterun = "<version>"`, with the
  `testing` feature as a dependency and a build-dependency, built in a copy
  whose `[patch.crates-io]` names the unpacked crate (a directory registry
  would have to vendor every dependency as well).
* **When** `cargo build`, `cargo test`.
* **Then** `build.rs` generates the harness; trials report the expected
  results; `cargo publish --dry-run` for the crate passes.
* **Cleanup.** Delete the consumer's `target/` and the registry directory.

### <a id="e5"></a>E5. TypeScript: a consumer installs the tarball and runs

* **Given** E1's `bdd-suite-runtime-<version>.tgz`; `samples/consumers/typescript`
  depending on it by that file only.
* **When** `npm ci`, `npx suiterun generate --config bddsuite.tests.yaml --out
  tests`, `node --test`, `npx suiterun run --name '*stock*'`.
* **Then** the bin, the `./testing` export and the `node:test` reporter
  resolve from `node_modules`; results are as expected.
* **Cleanup.** Delete `node_modules` and the generated tests.

### <a id="e6"></a>E6. PowerShell: a consumer installs the module and runs

* **Given** E1's module in a file PSResource repository; a fresh `pwsh -NoProfile`.
* **When** `Install-PSResource BddSuite -Repository <local> -Version <version>
  -Scope CurrentUser` into a temporary module path; `samples/consumers/powershell`
  imports it **by name**, runs its `suiterun.ps1 lint` and `run --name`, then
  generates and runs its Pester tests.
* **Then** expected results; `Get-Module BddSuite` reports the release version
  and the installed path, not `runtimes/`.
* **Cleanup.** Remove the temporary module path and the file repository.

### <a id="e7"></a>E7. The upstreamed flags and the worker rule hold in all five runtimes

* **Given** new corpus entries: `execute/names.yml` with `names:` globs (alone
  and with `tags`), a `list` entry with names, `execute/progress.yml` with an
  expected progress transcript, and `execute/worker-throws.yml` whose fixture
  action raises the language's most unusual failure (a non-`Error` value in
  TypeScript, a panic in Go and Rust, an exception type outside the old five in
  C#, an exception of a custom .NET type thrown from a PowerShell action).
* **When** each runtime's corpus test and its `suiterun` against those entries.
* **Then** the selected cases, the trace and the report equal the
  expectations; progress lines equal the transcript (durations masked); the
  throwing step fails with the message and later cases and teardown still run;
  a run with an observer produces the same trace as one without.
* **Cleanup.** None.

### <a id="e8"></a>E8. `bdd-suite:core` resolves to the runtime's own core everywhere

* **Given** a corpus catalog that imports `bdd-suite:core` with
  `bindings: [csharp]`.
* **When** each runtime lints and runs against it; the bundled
  `Build-Schema.ps1` generates the schema from it; the VS Code extension
  indexes it.
* **Then** findings, schema and index equal those of the same catalog
  importing `spec/core.catalog.yaml` by path, except every core action's
  bindings narrowed to `[csharp]`.
* **Cleanup.** None.

### <a id="e9"></a>E9. The VS Code extension alone lints a C#-only workspace

* **Given** a workspace with only `samples/consumers/csharp` and its suites,
  no TypeScript binding, default settings, the installed `.vsix`.
* **When** a suite is opened and a step's action is misspelled; the schema
  generator command runs.
* **Then** the misspelling is underlined within the usual delay, by the
  bundled linter; the schema regenerates through the bundled generator; no
  error mentions a missing TypeScript binding.
* **Cleanup.** Revert the edit.

### <a id="e10"></a>E10. The release pipeline dry run

* **Given** a pull request or a push that keeps the version.
* **When** CI runs.
* **Then** the version check passes (every manifest equals `package.json`);
  every package is packed once, E1 to E6 pass from local feeds, each publish
  step runs in dry-run mode (`dotnet nuget push` is skipped, `npm publish
  --dry-run`, `cargo publish --dry-run`, `Publish-PSResource -WhatIf`) and
  reports what it would publish; nothing reaches a registry.
* **Cleanup.** CI's temp directory.

### <a id="e11"></a>E11. The first public release installs from the registries (remote)

* **Given** the user's approval of the `release` environment; registry
  setup done (npm org, trusted publishers, Gallery key secret); a version not
  yet on any registry.
* **When** the release workflow publishes; then a clean job (fresh runner, no
  local feed, no checkout of `runtimes/`) installs each package from its
  public registry, polling up to 60 minutes per registry for indexing, and
  runs E2 to E6's consumers against them.
* **Then** every package is installable at the version, the consumers pass,
  the GitHub release lists every package with its registry link, the Go tag
  is at the release commit. Record the workflow run ID and each registry URL.
* **Cleanup.** Nothing is removed from a registry. A failed install is
  investigated; a broken package is fixed forward and the bad version
  unlisted, yanked or deprecated as in [5](#5-failure-rollback-and-cleanup).

### <a id="e12"></a>E12. update2 drops its copy (remote, consumer repository)

* **Given** an update2 worktree on a branch; E11's version on nuget.org,
  reachable through update2's restore sources.
* **When** `runtime/` and `Bdd.Suite.Patches.UnitTest` are removed; the
  projects reference `Bdd.Suite` and `Bdd.Suite.Testing` through
  `Directory.Packages.props`; the core catalog copy is replaced by
  `bdd-suite:core`; the `test/e2e/bdd` junction is no longer needed; its build,
  `Urp.Bvt.Suite.UnitTest` and `Urp.Bvt.Suite.MsTest` run; its suiterun runs a
  suite with `--name` and `--progress`.
* **Then** the build and tests pass with the same counts as on the copy; the
  progress lines are the ones its BVT tooling parses; `git grep "update2
  patch"` finds nothing. Its lab scenarios are update2's own and are not
  claimed here.
* **Cleanup.** The branch is kept for update2's review; nothing is pushed
  unless the user asks.
