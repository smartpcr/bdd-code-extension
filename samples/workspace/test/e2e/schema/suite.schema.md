# Test suite reference

Generated by `Build-Schema.ps1` from `suite.core.json`, `actions.catalog.yaml` (with the
catalogs and suite-schema extensions it imports) and `diagnostics.md`. Do not
edit this file: regenerate it, and run the generator with `-Check` in CI so a
stale copy fails the build.

A suite file is a YAML document. It is validated against `suite.schema.json`,
which is generated beside this page, and run by any binding

## A step

Every step carries these, whatever its action:

| Key | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `action` | string | yes |  |  |
| `given` | sentence |  |  | The state this step establishes. One Gherkin keyword per step, and the order within a list is given, then when, then then. |
| `when` | sentence |  |  | The behaviour this step exercises. |
| `then` | sentence |  |  | The outcome this step observes. Its expectation belongs in its own asserts. |
| `and` | sentence |  |  | Continues the keyword of the step before it. First in a list it is E212, because there is nothing to continue. |
| `why` | why |  |  |  |
| `timeoutSec` | limit |  |  | This step's own limit. The effective limit is the smaller of it and what remains of the case deadline: a step may shorten its share and may never lengthen it. An action that takes an internal bound, such as a poll or a drain wait, reads this same number. |
| `captureAs` | string |  |  | Publishes the return value of this step under this name, read as ${capture.<name>}. With a table, it publishes a list with one entry per row, in row order. |
| `ifCapture` | string |  |  | Runs the step only when this capture name or dotted object-field path is present. Null and false are present; an absent field skips the step. |
| `table` | table |  |  | Runs this step once per row, with ${row.<column>} bound to that row. |
| `asserts` | array |  |  | Checked immediately after this step and before the next one, inside this step's own limit. The case-level asserts block still runs after every step. |

[the actions](#the-actions) below. A parameter that is not in that list is
`E105`, which is what catches `valeu:` for `value:`.

## Reading a case as a scenario

A step may say which part of the scenario it is, and what it means, in the
language of the thing being tested rather than the language of the action.
The rules, all checked before anything runs:

* Exactly one of `given`, `when`, `then`, `and` per step. Two is `E212`.
* `and` continues the keyword above it. First in a list it is `E212`,
  because there is nothing to continue.
* The order inside one step list is `given`, then `when`, then `then`. Going
  backwards is `E212`. An `and` never counts as going backwards.
* A keyword is optional, so a suite can be labelled a case at a time. A list
  that labels some of its steps and not others is `W304`.
* A step may carry its own `asserts:`, checked immediately after it and
  before the next step. The case-level `asserts:` block is unchanged and
  still runs after every step. This is what makes a `then` step a real Then
  rather than a label on a step that asserts nothing.
* The sentence is what the report prints and what a failure names:
  `case greets / when the greeting is published (core.set)`.

A `then` step still needs an action, because the sentence is documentation
and the action is what runs. A `then` that only asserts uses the
side-effect-free `core.noop`.

### Table data

A step that carries a `table:` runs once per row, in row order, with
`${row.<column>}` bound to that row. Its `captureAs` publishes a list with
one entry per row, in the same order.

```yaml
      - given: a greeting for each person
        action: core.set
        value: Hello, ${row.name}
        captureAs: greetings
        table:
          - { name: Ada }
          - { name: Lin }
```

A case that carries `examples:` runs once per row and reports once per row,
named `<case name> [<column>=<value>, ...]`, with `${row.<column>}` bound for
the whole case, hooks and cleanup included. The tag filter selects the case,
which selects all of its rows.

Every row of a table declares the same columns, and no two rows are
identical: both are `E213`. A step `table:` inside a case that carries
`examples:` is `E213` as well, because there is one `row` namespace and two
row scopes would shadow each other. A `${row.<column>}` the table in scope
does not declare is `E301`.

## The order of everything

For a suite with cases C1 and C2 selected by the tag filter:

```
suite setup
  beforeEach -> C1 setup -> C1 steps -> C1 asserts -> C1 cleanup -> afterEach
  beforeEach -> C2 setup -> C2 steps -> C2 asserts -> C2 cleanup -> afterEach
suite teardown
```

Inside a step list, one step is:

```
the step runs -> its own asserts, if it has any -> the next step
```

and a step with a `table:` is that, once per row, in row order. A case with
`examples:` is the whole line above, once per row, with its own report entry
each time.

No hook is ever a passed or failed entry in the report, and no hook draws on
a case deadline. Failure is attributed like this:

| What fails | Cases affected | Still runs | Report |
| --- | --- | --- | --- |
| suite `setup` | all | `teardown` | every case errored with the setup message |
| `beforeEach` | that case | that case cleanup, `afterEach` | case failed |
| case `setup` | that case | that case cleanup, `afterEach` | case failed |
| a step | that case | remaining steps skipped, cleanup, `afterEach` | case failed |
| a step own assertion | that case | remaining steps skipped, cleanup, `afterEach` | case failed at that step |
| one row of a step table | that case | remaining rows and steps skipped, cleanup, `afterEach` | case failed, naming the row |
| an assertion | that case | remaining asserts skipped, cleanup, `afterEach` | case failed |
| one row of an outline | that row only | the next row, as its own case | that row entry failed |
| case `cleanup` | that case | `afterEach` | case failed, cleanup error appended |
| `afterEach` | that case | the next case | case failed, hook error appended |
| suite `teardown` | none | nothing | its own entry, exit code 1 |

## Where captures live

One bag per case. It starts as a copy of what the suite `setup` captured, so
`${capture.agent}` reaches a case that never produced it. `beforeEach` and the
case own `setup` write into that copy. Nothing a case captures is visible to
the next case, which is what lets cases run in any order.

## Reading a value

Anything between `${` and `}` is an expression. A string that is exactly one
expression yields that value with its type intact, so `timeoutSec: ${var.x}`
is a number; a string with an expression inside other text is substituted
into, so `name: run-${param.name}-a` is a string.

A path starts at one of four roots, and nothing else:

| Root | Reads |
| --- | --- |
| `capture.<name>` | what an earlier step in this case, or a hook before it, captured |
| `param.<name>` | a declared parameter, or a meta step parameter inside a definition |
| `var.<name>` | a calculated variable |
| `row.<column>` | one row of the table in scope: a step that carries a `table`, or a case that carries `examples` |
| `timeoutSec`, `defaults.<key>`, and the context keys a runtime extension adds | the run context |

A bare capture name is **not** a capture. `${origOwner}` is `E301`; the
spelling is `${capture.origOwner}`. There is one way to read a capture, which
is why a capture can never shadow a context key of the same name.

The operators and the closed function list of the expression language are
specified, case by case, by the conformance corpus (`conformance/expressions`),
which every runtime passes.

## Assertions

An assertion names a subject with `var:`, a dotted path into the capture bag,
and applies one or more operators. All of them must pass. A subject with no
operator is `E204`. An expected value may itself be an expression, so an
assertion can compare against a parameter or an earlier capture.

| Key | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `var` | string |  |  | A dotted path into the capture bag of the case. |
| `equals` | scalar |  |  | The subject as a string equals this, ignoring case. |
| `notEquals` | scalar |  |  | The subject as a string differs from this, ignoring case. |
| `contains` | scalar |  |  | A list subject has this as a member; any other subject has it as a substring, ignoring case. |
| `notContains` | scalar |  |  | The negation of contains, with the same coercion. |
| `startsWith` | scalar |  |  | The subject as a string begins with this, ignoring case. |
| `endsWith` | scalar |  |  | The subject as a string ends with this, ignoring case. |
| `matches` | string |  |  | The subject as a string matches this regular expression, ignoring case. Restricted to the subset RE2 and .NET agree on: a backreference, a lookahead or a lookbehind is E308. |
| `in` | array or string |  |  | The subject is a member of this list. |
| `gt` | exprNumber |  |  | Both sides as 64-bit floats, subject greater. A non-numeric operand fails the assertion with a type message, never silently as false. |
| `gte` | exprNumber |  |  | Both sides as 64-bit floats, subject greater or equal. A non-numeric operand fails with a type message. |
| `lt` | exprNumber |  |  | Both sides as 64-bit floats, subject smaller. A non-numeric operand fails with a type message. |
| `lte` | exprNumber |  |  | Both sides as 64-bit floats, subject smaller or equal. A non-numeric operand fails with a type message. |
| `count` | exprInteger |  |  | The subject is a list whose length equals this. |
| `isTrue` | boolean |  |  | The subject is the boolean true, not a truthy string. |
| `isFalse` | boolean |  |  | The subject is the boolean false, not a falsy string. |
| `isNull` | boolean |  |  | The path is absent or null. |
| `isNotNull` | boolean |  |  | The path is present and not null. |
| `script` | string |  |  | A PowerShell expression that must return truthy. Implemented by the PowerShell binding only. |

## Limits

```
case deadline  = case.timeoutSec or defaults.timeoutSec or 600
step deadline  = min(step.timeoutSec or infinity, what remains of the case deadline)
hook deadline  = the hook own key, independent of the case deadline
```

The runner fails a case that exceeds its deadline. The ceiling each limit
is checked against is in [diagnostics.md](diagnostics.md); a runtime
extension may add a stricter one, for example for suites with a given tag.

timeout on it is reported as abandoned rather than cancelled.

### `wait`

Sleep for a number of seconds, or poll a step until a condition holds.

Bindings: `powershell`, `csharp`, `go`, `rust`, `typescript`. Interruptible: true.

## Diagnostics

Every code, from [diagnostics.md](diagnostics.md), which also states the
output formats and the sort order a `--json` run writes.

| Code | Severity | Meaning |
| --- | --- | --- |
| `E100` | error | The file is not valid YAML, or does not hold a mapping, so nothing below can be checked. The position is the start of the file: four YAML parsers stop in four places on the same broken file, so where one stopped is not something two bindings can be held to. The message may say where, and messages are not compared. |
| `E101` | error | Unknown key. The nearest legal key at that position is suggested. This is the code that catches `assert:` for `asserts:` and `timeout:` for `timeoutSec:`. |
| `E102` | error | A required key is missing. The position is the object that should carry it. |
| `E103` | error | A key has the wrong type: a string where a list belongs, an object where a number belongs. |
| `E104` | error | Unknown action name. The nearest action in the catalog is suggested. |
| `E105` | error | Unknown parameter for a known action. The action's own parameters are what the suggestion is drawn from. |
| `E201` | error | The selected binding does not implement this action. The message names the action, the selected binding and the bindings that do implement it. Reported only under `--binding-check`. |
| `E202` | error | Two cases in one suite have the same name. A report cannot tell them apart. |
| `E203` | error | Two steps in one case capture the same name. The second would silently replace the first. |
| `E204` | error | An assertion names a subject and no comparison. This is what catches `equal:` being accepted as a key and then asserting nothing. |
| `E205` | error | A limit is missing where one is required, zero, negative, or above its ceiling. The message names the limit, where it was declared and the ceiling it broke. |
| `E206` | error | A case uses a meta step the suite does not declare. |
| `E207` | error | Meta steps form a cycle, or nest deeper than five. |
| `E208` | error | A meta step use site omits a required parameter or passes one the definition does not declare. |
| `E209` | error | A local declaration reuses an imported name without `override: true`. The message names the library it came from. |
| `E210` | error | A parameter has no value and no default at any level, or a `--param` names a parameter the suite does not declare. |
| `E211` | error | An imported library declares `tests` or a hook. A library declares `params`, `vars`, `metaSteps` and `defaults`, and nothing that runs. |
| `E212` | error | Gherkin keywords are misused: two on one step, an `and` with nothing before it to continue, or a keyword that goes backwards through the `given`, `when`, `then` order. |
| `E213` | error | A table or an `examples` block is empty, has rows whose columns differ, repeats a column, repeats a row, or is a step table inside a case that is already an outline. |
| `E301` | error | A `${...}` reference resolves to nothing. The legal roots are `capture`, `param`, `var`, `row` inside a table or an outline, and the bare context keys. A bare capture name is this code, with `${capture.<name>}` as the suggestion, and so is a `row` column the table does not declare. |
| `E302` | error | A dotted path is absent from the declared capture shape of the action that produced it. Only shapes the catalog closes are checked; an action whose capture shape is open, such as an API response, cannot be checked this way and is not. |
| `E303` | error | A capture is read before any step, hook or import produces it. |
| `E304` | error | A meta step exports a name that none of its steps captures. |
| `E305` | error | Syntax error inside `${ }`. The message names the offending token. |
| `E306` | error | Unknown function. The nearest function in the closed list is suggested. |
| `E307` | error | A function is called with the wrong number or type of arguments. |
| `E308` | error | A regular expression uses a construct outside the subset the four bindings share: a backreference, a lookahead or a lookbehind. |
| `E309` | error | A non-deterministic function (`env`, `uuid`, `nowIso`) is used where the value has to be stable, which is a `vars:` block the conformance corpus compares. |
| `W301` | warning | A capture is produced and never read, by a later step, an assertion or a cleanup. Either the step is doing nothing or an assertion is missing. |
| `W302` | warning | The action is marked deprecated in the catalog. |
| `W303` | warning | A parameter is declared and never read. |
| `W304` | warning | A step list labels some of its steps with a Gherkin keyword and not others, so the report reads half as a scenario and half as a list of calls. A suite can be labelled a case at a time, which is why this is a warning. |
