# A PowerShell consumer of the BddSuite module

A small workspace that uses the PowerShell runtime the way another repository
would: the module `BddSuite` by name and version, with no path into this
repository (docs/packages, E6).

| Part | What it is |
| --- | --- |
| `suiterun.ps1` | Its own `suiterun`: `#Requires` BddSuite at the release version, then `Invoke-BddSuiteCli` with the greeter's extension. |
| `schema/actions.catalog.yaml` | Its catalog: the core imported by name (`bdd-suite:core`) and two actions, `greet.say` and `greet.shout`; `suite.schema.json` and `suite.schema.md` beside it are generated by the spec's `Build-Schema.ps1`. |
| `suites/` | `greeting.yml` (offline) and `loud.yml`, which uses `greet.shout`, an action `bddsuite.tests.yaml` does not list as offline, so its test skips unless `BDD_SUITE_ALLOW_GUARDED=1`. |
| `Greeter/` | Its extension module, `Greeter.psm1`, and its actions, `actions/Greet.ps1`. |
| `bddsuite.tests.yaml` | Its suites as Pester tests, generated into `tests/` by `suiterun.ps1 generate --config bddsuite.tests.yaml --out tests`. |

Until the module is on the PowerShell Gallery, `run-e6.ps1` installs it from a
file repository that `scripts/local-feeds.ps1 -Language powershell` fills:

```powershell
pwsh -File samples/consumers/powershell/run-e6.ps1
```

It saves the module, with the `powershell-yaml` it requires, from that
repository into `artifacts/e6/modules` (a module path of the run's own, not the
user's), proves `Import-Module BddSuite` by name loads the release version
from there, checks its `suiterun.ps1`'s `lint`, `list --name` and
`run --name --progress`, generates the Pester tests and runs them: every case
passes but the guarded one, which skips; all pass with
`BDD_SUITE_ALLOW_GUARDED=1`; a full-name filter selects one case.
